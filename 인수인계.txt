3. 제공 바이너리 분석 결과
--------------------------------------------------------------------------------
- 3개 모두 x64 PE, MinGW(Fedora, GCC 15/16)로 빌드. libjabcode.dll 은 libpng 1.6.37 / libtiff / zlib
  정적 포함(2.6 MB), import는 KERNEL32/msvcrt 뿐. exe 2개는 libjabcode.dll 을 import.
- DLL export: 공식 jabcode(github.com/jabcode/jabcode, 헤더 VERSION "2.0.0") API 그대로
  createEncode, destroyEncode, generateJABCode, decodeJABCode, decodeJABCodeEx, saveImage,
  readImage 등.
- 구조체(jabcode.h v2.0.0) — Windows x64와 Linux x64에서 오프셋 동일 (long 미사용):
    jab_encode: color_number, symbol_number, module_size, master_symbol_width,
                master_symbol_height, palette*(+24), symbol_versions*(+32), symbol_ecc_levels*(+40),
                symbol_positions*(+48), symbols*(+56), bitmap*(+64) ; sizeof=72
    jab_bitmap: width,height,bits_per_pixel,bits_per_channel,channel_count (20B) + pixel[] (RGBA)
    jab_data:   int32 length + char data[]
- 주의: generateJABCode 는 성공 시 0 을 반환 (JAB_SUCCESS=1 아님!). 실패 코드 1~4
  (4 = "Message does not fit into the specified code").
- 주의: libjabcode 는 전역 PRNG 상태 static lcg64_seed (pseudo_random.c) 를 가짐 → 스레드 안전하지 않음.
  그래서 송신측은 멀티스레드가 아니라 멀티프로세스(ProcessPoolExecutor)로 프레임 생성.
- 주의: generateJABCode 는 enc 재사용 안전성이 불확실 → 매 프레임 createEncode/destroyEncode.
- 검증(Wine, 클라우드): MinGW로 만든 C 하네스로 DLL 로드 → offsetof 가 ctypes 정의와 일치
  (bitmap=64, versions=32, ecc=40, size=72), 인코드→디코드 왕복 20/20 성공.
  제공 jabcodeWriter.exe 출력 PNG → 우리 WASM 디코더로 원본과 바이트 일치.
- jabcodeWriter.exe 인자(폴백에서 사용): --input-file, --output, --color-number, --module-size,
  --symbol-version X Y, --ecc-level

4. 전송 프로토콜 (송신 jabfountain.py ↔ 수신 jabcore.js 가 비트 단위로 일치해야 함)
--------------------------------------------------------------------------------
[컨테이너] 파일 1개 → 바이트열 (리틀엔디언)
   0  4  magic b"JFC1"
   4  1  flags  bit0 = zlib 압축 (zlib.compress level 9, 5% 이상 줄 때만)
   5  1  reserved 0
   6  2  name_len u16
   8  4  원본 파일 크기 u32
  12  4  원본 CRC32 u32 (zlib.crc32)
  16  4  저장 데이터 길이 u32
  20  .  파일명 UTF-8 (basename, 1024B 초과 시 확장자 보존하며 절단) + 데이터
  → K = ceil(len/block_size) 블록으로 분할, 마지막 블록 0 패딩.
  수신측 해제: DecompressionStream('deflate')(=zlib 포맷) → 실패 시 fflate.unzlibSync.

[패킷] JAB Code 1프레임 = 패킷 1개, 헤더 28B (struct "<2sBBIIHIIH" + CRC u32)
   0  2  b"JF"
   2  1  version = 1
   3  1  flags (0)
   4  4  session u32
   8  4  K u32
  12  2  block_size u16  (용량-28 을 4의 배수로 내림 → JS Uint32 XOR 최적)
  14  4  컨테이너 전체 길이 u32
  18  4  seed u32 (패킷 번호)
  22  2  degree u16
  24  4  CRC32( bytes[0:24] + payload )
  28  .  payload (block_size)

[파운틴 코드]
- 모든 패킷 = 소스 블록 degree 개의 XOR. (시스테매틱 단계 없음 — 아래 설계 근거 참고)
- 블록 인덱스: rng = mulberry32((seed ^ session) >>> 0); i = rng() % K 반복, 중복 제외, degree 개.
  mulberry32 (JS):
    a = (a + 0x6D2B79F5)|0; t = Math.imul(a ^ (a>>>15), 1|a);
    t = (t + Math.imul(t ^ (t>>>7), 61|t)) ^ t; return (t ^ (t>>>14))>>>0;
  Python 구현(Mulberry32 클래스)은 & 0xFFFFFFFF 마스킹으로 동일 결과 (실제 종단 테스트로 검증됨).
- degree 분포(송신측만 앎, 헤더에 기록): K<=8 → [1,K] 균등, 그 외 [int(lnK/2)+2, min(K,int(2lnK)+4)] 균등.
  degree는 random.Random((session<<32)|seed).randint 로 결정적으로 생성.
  ※ 반드시 홀/짝 혼합: 짝수 degree만 쓰면 GF(2)에서 모든 행이 짝수 가중치 → rank 최대 K-1 → 복원 불가
    (실제로 이 버그를 시뮬레이션에서 발견함).
- 수신 디코더: 온라인 가우스 소거. 행 = (Uint32Array 마스크 W=ceil(K/32) 워드, Uint32Array 데이터 D워드).
  최상위 set bit h 를 피벗 키로, 피벗 있으면 XOR 하며 내려가고 없으면 저장(rank++). 0이 되면 종속(useless).
  rank==K 이면 h 오름차순으로 역대입해 해 계산.
  성능: 1 MB(K=3049, bs=328) → add 총 289ms + 역대입 161ms (Node, 데스크톱).
- session = (crc32(container) ^ (crc32("colors/version/ecc/block") << 1)) & 0xFFFFFFFF (0이면 1).
  → 같은 파일·설정이면 송신을 재시작해도 세션 동일 → 수신 진행 유지. 재시작 시 시작 seed는 랜덤(31bit).

[설계 근거 — 시뮬레이션 결과]
- 최초 설계: 시스테매틱(seed<K는 원본 블록) + Robust Soliton + 피일링(peeling) 디코더.
  → 손실 30%에서 오버헤드 30~70% 로 나쁨. 원인: 놓친 원본 블록을 저차수 repair 패킷이 커버할 확률이 낮음
    (coupon collector). GE 폴백을 붙여도 커버리지 문제는 해결 안 됨.
- 최종: 비시스테매틱 + 균등 degree + 온라인 GE.
  결과(오버헤드): K=50 2%, K=300 0.3%, K=1000 0.1%, K=5 정도의 아주 작은 K에서만 수십 %.
  카메라 수신은 어차피 중간부터 들어오고 무작위로 놓치므로 비시스테매틱이 유리.

--------------------------------------------------------------------------------
jabcode_backend.py
- DllBackend: ctypes.CDLL, os.add_dll_directory. generate(data, colors, version, ecc):
  createEncode(colors,1) → module_size=1, symbol_versions[0]=(v,v), symbol_ecc_levels[0]=ecc →
  jab_data 버퍼 직접 구성 → generateJABCode(rc==0 성공) → bitmap 헤더 다음 주소에서 w*h*4 RGBA 복사
  → destroyEncode. 1모듈 = 1픽셀 이미지 반환 (화면 확대는 Qt에서 nearest).
- ExeBackend: 임시폴더에 in.bin 쓰고 jabcodeWriter.exe 실행(CREATE_NO_WINDOW) → PNG를 PIL로 읽음.
- load_backend(prefer): DLL 우선, 실패 시 EXE. 검색 경로: JABCODE_DIR 환경변수, sender, 상위,
  상위의 상위(= C:\play_claude), cwd. Windows는 libjabcode.dll / jabcodeWriter.exe,
  Linux는 libjabcode.so 등.
- probe_capacity(): 0x80~0xFF 랜덤 바이트(최악 = 전부 byte mode)로 이진 탐색해 최대 바이트 수 측정, 캐시.
  측정치(리눅스 .so, 동일 소스): 8색 v6 e5=243B, v8 e5=359B(→블록 328), v10 e3=636B, v10 e5=487B,
  v14 e5=811B, v20 e5=1454B / 4색 v8 e5 ≈ 2/3 수준.
  생성 시간: v8~10 ≈ 20~50ms, v14~20 ≈ 50~80ms (마스크 8종 평가가 비쌈) → 멀티프로세스 필요.

framegen.py
- ProcessPoolExecutor(max_workers=min(6, cpu-1)), initializer가 각 프로세스에서 backend 로드 +
  FountainEncoder 생성(container 전체를 initargs로 피클 전달). make_frame(seed) → (seed, degree, w, h, rgba).
- Windows spawn 방식이므로 jab_sender.py 는 main() 안에서 mp.freeze_support() + __main__ 가드.

jab_sender.py (PySide6)
- 좌측 패널: 파일 선택(드래그&드롭), 심볼 버전(1~32, 기본 8 = 49×49 모듈),
  (색 수 선택은 2026-10-02 제거 — jabcode_backend.COLOR_NUMBER = 8 고정, 17장),
  ECC(1~10, 기본 5), fps(1~60, 기본 6), zlib 압축 체크, 생성 엔진(DLL/EXE), 수신 페이지 URL + QR 버튼,
  정보 패널(세션ID, 심볼, 프레임당 데이터, K, 최소 필요 프레임 K+2, 예상 시간, 이론 속도, 표시 프레임 수,
  실제 fps, 버퍼, 생성 지연 경고).
- CodeView(QWidget): 흰 배경, 정수 배율 nearest 확대, 주위 4모듈 quiet zone 확보.
- Producer(QThread): 풀에 seed 순서대로 제출(작업자×2 선행), 결과를 deque에 적재(최대 fps×2, 최소 8).
  JabCodeError 프레임은 건너뜀. QTimer(PreciseTimer) 1000/fps 마다 pop 해서 표시, 비면 underrun 카운트.
- 설정 변경 → mark_dirty → 실행 중이면 stop 후 재시작(용량 재측정).
- 단축키: F11/더블클릭 전체화면(사이드 패널 숨김), Esc 복귀, Space 시작/일시정지.
- 수신 URL: receiver_url_from_file() (sender 또는 상위의 receiver_url.txt) > QSettings("jabtx","sender")
  > 빈칸. QR은 qrcode 패키지 사용.
- QSettings 키: prefer, receiver_url, last_dir.

  사용자 피드백 없음 (Python 3.14 + PySide6 6.11.2 조합).

6. WASM 디코더 (wasm/)
--------------------------------------------------------------------------------
- emsdk 설치는 storage.googleapis.com 차단으로 실패 → wasi-sdk 25 (GitHub 릴리스) 로 빌드.
- 빌드: clang --target=wasm32-wasi -O3 -flto -mexec-model=reactor, jabcode/src/jabcode/*.c 중 image.c
  제외(png/tiff 의존), -Wl,--export=malloc,free, stack 2MB, initial-memory 16MB(성장 가능), strip.
  SIMD(-msimd128) 빌드도 해봤으나 속도 차이 없어 제거.
- 임포트: wasi_snapshot_preview1 의 fd_write, fd_close, fd_seek, fd_fdstat_get, random_get →
  jabcore.js 의 최소 shim이 제공(fd_write는 로그 버퍼에 누적).
- export: memory, _initialize, malloc, free,
    jw_buffer(w,h) → RGBA 버퍼 포인터 (jab_bitmap 재사용)
    jw_decode(mode) → 길이(>=0) 또는 -1-status   (내부적으로 decodeJABCodeEx + 전역 g_syms[61])
    jw_result() → 데이터 포인터
    jw_status()
    jw_geom(float* out11) → [side_x, side_y, module_size, FP0x,FP0y, FP1x,FP1y, FP2x,FP2y, FP3x,FP3y], 1/0
  FP 순서: 좌상, 우상, 우하, 좌하. FP 중심은 심볼 모듈 좌표 (3.5,3.5)/(side-3.5, ...) 에 해당
  (검증: 6px/모듈 + 24px 여백 이미지에서 FP0=(45,45)=24+3.5×6).
  detectMaster는 파인더 패턴 4개를 찾으면 디코드 실패여도 pattern_positions/module_size 를 채운다
  → 감지됐지만 못 읽은 경우(status 1)도 위치를 얻을 수 있음.
- 디코드 시간(데스크톱 Node): 1280×720 ≈ 100~150ms, 해상도를 줄여도 크게 안 빨라짐(LDPC/검출 고정비용).
  축소하면 인식률만 떨어짐(720→440 크롭 축소 시 성공 64→45).
- decodeJABCodeEx 는 입력 bitmap 을 balanceRGB 로 제자리 수정함(매번 새로 복사하므로 무관).

7. 수신 웹앱 (receiver/)
--------------------------------------------------------------------------------
jabcore.js: crc32, mulberry32, blockIndices, parsePacket(CRC·범위 검증), FountainDecoder,
  parseContainer(async, 압축 해제 + 크기·CRC 검증), loadJab(wasm) → {decode, decodeEx, memoryBytes, log}.
  decodeEx → {data|null, status, geom|null}.

decode-worker.js: init 시 fetch(jabcode.wasm) → WebAssembly.compile(arrayBuffer) (MIME 무관).
  frame 메시지 {id,w,h,buf} → decodeEx → {type:'result', id, status, ms, buf, data, geom} (transfer).
  메모리 384MB 초과 또는 trap 시 인스턴스 재생성. (변수명 module 사용 금지 — jabcore.js UMD 판별과 충돌했던 버그 있었음)

fountain-worker.js: importScripts(jabcore.js, fflate.js). 세션별 디코더 Map(최대 4), 완료 세션 Set.
  메시지: progress{session,k,rank,bs,total,received,useless,useful,isNew}, assembling, file{name,data,frames},
  error, invalid, dup-finished.

app.js 주요 동작
- 워커 수: 기본 max(1, min(4, hardwareConcurrency-1)), 설정에서 변경.
- 카메라: getUserMedia({facingMode: ideal 'environment', width/height ideal 1920×1080(설정: 720p/4K),
  frameRate 30}), 실패 시 {video:true} 재시도. 오류 이름별 한국어 안내. playsinline/muted.
  연속 초점(focusMode continuous) 시도, zoom 지원 시 슬라이더 표시, Wake Lock 요청, 카메라 목록 선택.
- 프레임 분배: requestVideoFrameCallback 있으면 새 비디오 프레임만 전송, 없으면 30ms 간격 rAF.
  idle 워커마다 canvas drawImage → getImageData → buffer transfer. 분석 크기 최대 1000px(설정 720/1400).
- 분석 영역(설정 "인식 영역" 슬라이더): 기본 100 = 전체 화면(가이드 숨김). 100 미만이면 가운데 정사각
  (짧은 변 × 비율) 크롭 + 점선 가이드 표시.
- ROI 추적(v1.1, chooseRegion/roiResult): 위치(geom)를 얻으면 파인더 패턴 중심 기준 정사각(FP 간격×2.2,
  최소 320px)만 원해상도로 잘라 분석. 700ms 동안 위치 없음 또는 ROI 프레임 4연속 실패 시 탐색 모드.
  탐색 모드: [전체(축소), 가운데 타일, 앞쪽 끝 타일, 전체, 가운데, 뒤쪽 끝] 순환 (타일 = 짧은 변 정사각,
  긴 축을 따라 위치). 슬라이더 < 100 이면 탐색 시 가이드 영역만 사용. HUD 칩 "추적 W×H"/"탐색 중".
  · 근거: 1080p 전체 화면을 1000px로 줄이면 0.52배 → 코드가 화면 높이의 ~35% 미만이면 모듈 < 3.5px로 검출 실패.
- 전송률(v1.1): 세션별 첫 패킷 인식 시각(rateT0) ~ rank==K 시각(rateT1), min(rank×bs, total)/경과초.
  1초 미만은 "측정 중". KB/s(10 미만 소수 2자리) / MB/s. 통계 "전송률", 완료 카드·상태 메시지에 평균 표시.
  ※ 이전 기본(가운데 85%)은 코드가 가이드 밖으로 조금만 나가도 검출 실패 → 움직이는 영상 인식률 15%.
    전체 화면으로 바꾼 후 75%, 전송 테스트 인식률 98%.
- 추적 박스(사용자 요청으로 '초록 가이드 플래시' 제거 후 구현):
  frameMeta(id → {sx, sy, sc(축소비), t(캡처 시각), video 여부}) 보관 → 결과의 geom 4점으로
  호모그래피(8×8 가우스 소거) 계산 → 심볼 네 모서리 (0,0)(S,0)(S,S)(0,S) → 분석 이미지 → 비디오 좌표
  → object-fit:contain 매핑으로 화면 좌표 → <canvas id="ov"> (DPR 대응)에 그림.
  · 늦게 도착한(캡처 시각이 더 오래된) 결과는 무시.
  · 등속 예측: 직전 결과와의 꼭짓점 속도(지수 평활 0.4/0.6) × min(250ms, 캡처 후 경과)×0.8 만큼 앞당김.
  · 표시 위치는 목표로 지수 보간(시정수 55ms). 0.3초 후부터 페이드, 0.7초 지나면 사라짐.
  · 색: 초록 "✓ 수신"(디코드 성공) / 주황 "인식 중…"(검출만). 반투명 채움 + 외곽선 + 굵은 모서리 브래킷 + 라벨.
  · 동영상 파일 모드에서도 동작(video 소스일 때), 사진 모드에서는 표시 안 함.
- HUD 칩: 분석 fps(최근 2초), 인식률(최근 40프레임), 카메라 해상도.
- 진행: 진행률·블록 rank/K·유효 프레임(중복)·남은 시간(유효 패킷 수신 속도 기반)·전송 크기·세션.

  iOS 외에는 자동 다운로드 클릭. 같은 세션 프레임이 계속 보이면 "✅ 이름 수신 완료 — 송신 정지해도 됨".

7. VibeDrop 무료 사이트 만료(30일 무방문) / claim 여부 — 10장 참고.
8. 큰 파일(수 MB↑)은 광학 대역폭(~2KB/s 이론) 때문에 비현실적. 4GB 초과 미지원(u32 필드).
